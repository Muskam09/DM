## ЧАСТИНА А. Модулі бекенду

Бекенд — це один FastAPI-застосунок (`scraper/bot_server.py`), який поєднує дві
зовнішні інтеграції: **LLM Gemini** (екстракція слотів) і **Chatwoot** (омніканальна
платформа — джерело вхідних повідомлень і адресат вихідних). Обидві інтеграції
реалізовані всередині `bot_server.py`; окремих пакетів/клієнтських класів для них
немає.

### А.1. Модуль інтеграції з LLM (Gemini)

**Шлях:** `scraper/bot_server.py` (ініціалізація, промпт, виклики) +
`scraper/dialogue_engine.py` (парсинг відповіді).

**Відповідальність.** LLM зведено **виключно до екстракції/класифікації**: він
читає історію діалогу і повертає структурований JSON зі «слотами» (тема, кімнати,
дати, гості, FAQ-шаблон, харчування). Він **ніколи** не рахує ціну/дату/день тижня і
**не пише клієнтський текст** (`scraper/bot_server.py:155-157`, коментар перед
`EXTRACTION_PROMPT`).

**Конфігурація клієнта** (`scraper/bot_server.py:8, 18, 23-24`):

```python
from google import genai                                    # рядок 8
GEMINI_API_KEY = os.getenv("GEMINI_API_KEY")                 # рядок 18 (значення = ***)
ai_client = genai.Client(api_key=GEMINI_API_KEY)            # рядок 23
MODEL_NAME = 'gemini-2.5-flash-lite'                        # рядок 24
```

**Ключові функції з сигнатурами:**

| Функція | Шлях:рядки | Роль |
|---|---|---|
| `async generate_with_retry(prompt: str, retries: int = 3, base_delay: int = 2)` | `bot_server.py:139-153` | виклик LLM з експоненційним backoff на транзієнтних збоях |
| `_is_retryable_llm_error(exc) -> bool` | `bot_server.py:131-136` | класифікація «транзієнтний / фатальний» збій |
| `parse_slots(text: str) -> Dict` | `dialogue_engine.py:60-86` | жорсткий парсинг JSON-відповіді у слоти |
| `_denull(v)` / `_clean_room(r: Dict) -> Dict` | `dialogue_engine.py:47-57` | нормалізація «stringy-null» → `None` |

**Як формується запит/промпт до Gemini.**

Промпт — це велика статична текст-константа `EXTRACTION_PROMPT`
(`bot_server.py:158-251`) з трьома плейсхолдерами. Перед кожним викликом вони
підставляються звичайним `str.replace` (`bot_server.py:450-453`):

```python
prompt = (EXTRACTION_PROMPT
          .replace("%%TODAY%%", date.today().isoformat())
          .replace("%%HISTORY%%", dialogue_history or "(порожня)")
          .replace("%%MESSAGE%%", user_message))
```

- `%%TODAY%%` — сьогоднішня дата (для розрахунку відносних дат «завтра», днів тижня).
- `%%HISTORY%%` — уся історія діалогу, зібрана з Chatwoot у форматі `Клієнт: … / Бот: …`
  (`bot_server.py:419-428`).
- `%%MESSAGE%%` — нове повідомлення клієнта.

Промпт **жорстко структурує вихід**: вимагає повернути ВИКЛЮЧНО JSON без markdown і
пояснень (`bot_server.py:162`), задає точну схему полів (`topic`, `rooms[]`,
`faq_template`, `meals`) з переліком дозволених значень (`bot_server.py:163-168`), і
явно **забороняє** генерувати прозу/описи/внутрішні назви кімнат
(`bot_server.py:170`). Далі йдуть детальні правила заповнення слотів (розбір дат,
дні тижня, родинні слова → гості, діти, УБД, харчування) — приблизно 90 рядків
інструкцій.

Сам виклик — асинхронний, через офіційний SDK (`bot_server.py:145-146`):

```python
return await ai_client.aio.models.generate_content(
    model=MODEL_NAME, contents=prompt)
```

**Як парситься й обробляється відповідь.**

1. Виклик у `_handle_incoming` (`bot_server.py:454-456`):
   ```python
   extraction = await generate_with_retry(prompt)
   slots = dialogue_engine.parse_slots(extraction.text)
   ```
   Використовується поле `extraction.text` (сирий текст відповіді моделі).

2. `parse_slots` (`dialogue_engine.py:60-86`) — жорсткий, «пуленепробивний» парсер:
   - зрізає markdown-огортку ```` ```json ```` регуляркою (`:67`);
   - витягує підрядок від першої `{` до останньої `}` (`re.search(r"\{.*\}", …)`, `:68-70`);
   - `json.loads`; при `JSONDecodeError`/`TypeError` → повертає безпечний
     `{"topic": "greeting", "rooms": []}` (`:71-74`);
   - валідує типи: якщо результат не `dict` → знову «greeting» (`:75-76`);
   - проставляє дефолти `topic`/`rooms`, нормалізує кожну кімнату через `_clean_room`
     (`:77-86`).

3. `_denull` (`dialogue_engine.py:44-51`) знешкоджує реальний дефект малого LLM:
   рядкові «null»/«none»/«»/«-» перетворюються на Python `None`, щоб далі по коду
   ніде не з'явився фейковий тип кімнати `"null"`:
   ```python
   _NULLISH = {"null", "none", "nil", "n/a", "na", "-", ""}
   ```

Далі отримані `slots` більше **не потрапляють у жодну генерацію тексту** — їх
обробляє детермінований `dialogue_engine.plan()` / `finalize_quote()`.

### А.2. Модуль інтеграції з Chatwoot

**Шлях:** `scraper/bot_server.py`.

**Відповідальність.** Приймає вебхуки нових повідомлень, читає історію та мітки
розмови, надсилає відповіді, керує мітками (label) для передачі діалогу людині.
Транспорт — синхронний `requests` (`bot_server.py:4`) до REST API Chatwoot; у
асинхронному коді загорнутий у `asyncio.to_thread` (напр. `bot_server.py:308`).

**Конфігурація** (`bot_server.py:19-21`):

```python
CHATWOOT_URL = os.getenv("CHATWOOT_URL", "http://rails:3000")
CHATWOOT_TOKEN = os.getenv("CHATWOOT_TOKEN")     # значення = ***
ACCOUNT_ID = os.getenv("CHATWOOT_ACCOUNT_ID", "1")
```

Автентифікація — заголовок `api_access_token: ***` у кожному запиті
(`bot_server.py:35, 55, 74, 86`).

**Ключові функції з сигнатурами:**

| Функція | Шлях:рядки | Роль |
|---|---|---|
| `send_chatwoot_message(conversation_id: int, message_text: str)` | `bot_server.py:32-50` | POST вихідного повідомлення (`message_type: "outgoing"`) |
| `get_chatwoot_history(conversation_id: int)` | `bot_server.py:52-69` | GET історії, сортування за `id`, толерантність до формату (`list`/`dict`) |
| `get_conversation_labels(conversation_id: int)` | `bot_server.py:71-81` | GET списку міток розмови |
| `add_conversation_label(conversation_id: int, label: str)` | `bot_server.py:83-97` | додати мітку (union до наявних) |
| `async _deliver(conversation_id: int, text: str)` | `bot_server.py:305-309` | розбити текст по `[SPLIT]` і надіслати частинами з паузою 1.5 с |
| `async chatwoot_webhook(request, background_tasks)` (ендпойнт `@app.post("/webhook")`) | `bot_server.py:894-925` | точка входу вебхука |

**Як формується запит (надсилання).** Тіло — фіксований JSON (`bot_server.py:38-42`):

```python
payload = {"content": message_text.strip(),
           "message_type": "outgoing", "private": False}
response = requests.post(url, json=payload, headers=headers, timeout=5)
```

Кожен HTTP-виклик має `timeout=5` і обгорнутий у `try/except`, що лише логує
помилку мережі й не валить процес (`bot_server.py:43-50, 58-68, 90-97`).

**Як обробляється вхід (вебхук).** `chatwoot_webhook` (`bot_server.py:894-925`):
- парсить JSON, при помилці → `{"status": "ignored"}` (`:896-899`);
- реагує лише на `event == "message_created"` і `message_type in ("incoming", 0)` —
  приймаються **обидві** форми (рядок і int), бо різні канали Chatwoot надсилають
  по-різному (`bot_server.py:903-907`);
- ігнорує приватні нотатки агента (`private`) (`:908-909`);
- дістає `conversation_id`, `content`, наявність вкладення `has_attachment`
  (скрін оплати може прийти без тексту) (`:910-914`);
- **не блокує вебхук**: реальна обробка ставиться у `BackgroundTasks` з порядковим
  номером `seq` (`bot_server.py:916-919`), а ендпойнт одразу повертає `{"status": "ok"}`.

**Як обробляється відповідь Chatwoot.** Відповіді на GET нормалізуються під різні
формати (`get_chatwoot_history` приймає `list` або `dict` з ключами
`payload`/`messages`/`data`, `bot_server.py:61-66`); статуси POST перевіряються, але
не кидають виняток — лише логуються (напр. `bot_server.py:45-48, 92-95`).

## ЧАСТИНА Б. Рівень контролю галюцинацій і надійності

Архітектурний принцип: **LLM екстрагує, Python вирішує**. Модель зведена до
класифікатора, а всі рішення про гроші/календар/текст ухвалює детермінований,
покритий тестами код (`dialogue_engine.py`, `bot_logic.py`, `pricing_engine.py`).
Нижче — кожен механізм окремо.

### Б.1. Аварійні вимикачі (circuit breakers)

#### Б.1.1. Retry з експоненційним backoff на виклику LLM
- **Де:** `bot_server.py:131-153`.
- **Що запускає:** будь-який виняток при `generate_content`; `_is_retryable_llm_error`
  перевіряє рядок помилки на маркери транзієнтності (`"503"`, `"429"`, `"unavailable"`,
  `"resource_exhausted"`, `"overloaded"`, `"timeout"`, `"500"`, …).
- **Що робить:** для транзієнтного збою чекає `2s`, потім `4s` (`base_delay * 2**attempt`)
  і повторює; максимум 3 спроби. **Фатальний** (нетранзієнтний) збій — одразу `raise`,
  щоб не марнувати час.
- **Поведінка при спрацюванні:** після вичерпання спроб виняток піднімається до
  `_handle_incoming` → шлях деградації Б.1.2.

```python
if attempt < retries - 1 and _is_retryable_llm_error(e):
    wait = base_delay * (2 ** attempt)        # 2s, 4s
    await asyncio.sleep(wait)
else:
    raise
```

#### Б.1.2. Graceful degradation при недоступності LLM
- **Де:** `bot_server.py:454-471`.
- **Що запускає:** `generate_with_retry`/`parse_slots` кинули виняток (LLM недоступний
  після ретраїв).
- **Що робить / шлях деградації:** ніколи не лишає клієнта без відповіді — надсилає
  холдинг-повідомлення `templates.ERROR_LLM_DOWN` **один раз** (дедуплікація за
  останнім повідомленням бота), тегує розмову міткою `Instagram` для передачі людині,
  і **запускає 5-хвилинний кулдаун** (`_cooldowns[conversation_id] = time.time()`).

```python
except Exception as e:
    if _superseded(conversation_id, seq): return
    if last_bot != templates.ERROR_LLM_DOWN.strip():
        await _deliver(conversation_id, templates.ERROR_LLM_DOWN)
    await asyncio.to_thread(add_conversation_label, conversation_id, bot_logic.INSTAGRAM_LABEL)
    _cooldowns[conversation_id] = time.time()
    return
```

#### Б.1.3. Кулдаун після збою (silent cooldown)
- **Де:** `bot_server.py:365-370`; константа `COOLDOWN_TTL = 300` (`bot_server.py:30`).
- **Що запускає:** нове повідомлення в розмові, де менш ніж 5 хв тому був збій LLM.
- **Що робить:** бот **мовчить** увесь період кулдауну, щоб людина-менеджер перехопила
  діалог, а бот не «падав» на кожному новому повідомленні.

#### Б.1.4. Kill-switch / mute за мітками
- **Де:** `bot_server.py:357-363`; `bot_logic.is_muted` (`bot_logic.py:1179-1181`);
  константи `MUTE_LABELS = [ORDER_LABEL="Замовлено", MARKED_LABEL="Позначено"]`
  (`bot_logic.py:1151-1154`).
- **Що запускає:** наявність будь-якої mute-мітки на розмові (людина перехопила діалог
  або завершила угоду).
- **Що робить:** **жорсткий стоп на самому початку** обробки — без LLM, без відповіді,
  без подальших запитів. Це перший guard у `_handle_incoming`.

#### Б.1.5. Помилка скрапера / бази доступності
- **Де:** `hotel_scraper.py:44-50` (повертає `{"error": …}` якщо сітка не завантажилась);
  `bot_server.py:109-115` (`get_hotel_data_cached` ловить виняток → `return None`);
  `bot_server.py:737-741` (порожні дані → холдинг «технічна затримка бази…» і вихід).
- **Що робить:** якщо календар недоступний — бот не вигадує доступність, а чесно
  просить трохи почекати й передає людині.

### Б.2. Фільтрація вхідних і вихідних даних

#### Б.2.1. Вхідні детерміновані guard-и (до LLM)
У `_handle_incoming` перед екстракцією стоїть ланцюг чистих перевірок
(`bot_logic`), кожна з яких — короткий вихід:

| Guard | Детектор (`bot_logic.py`) | Запуск | Дія при спрацюванні |
|---|---|---|---|
| Бартер/колаборація | `is_barter` (`172-182`) | маркери «бартер», «блогер», «рілс», «взаємопіар»… | мовчання + мітка `Instagram` (`bot_server.py:375-378`) |
| Спам / B2B | `is_spam` (`149-164`) | маркери «стікер», «таргетолог», «smm», «просування сторінк»… | повне ігнорування (`bot_server.py:381-383`) |
| Оплата | `is_payment_intent` (`1170-1176`) | вкладення-скрін АБО ключові слова «оплатив», «квитанц», «чек»… | `PAYMENT_RECEIVED_HANDOFF` + мітки `Замовлено`+`Instagram`, замовкання (`bot_server.py:387-394`) |
| Телефон | `contains_phone_number` (`1141-1145`) | токен з 9-13 цифр (виключає дати/ціни) | `PHONE_RECEIVED`, передача менеджеру (`bot_server.py:397-400`) |
| Booking.com | `is_booking_com_question` (`336-339`) | «booking»/«букінг» | `BOOKING_COM` + мітка `Instagram` (`bot_server.py:405-409`) |

Ці guard-и працюють **до** виклику Gemini — так «важкі» рішення (оплата, спам,
велика група) не залежать від нечіткої класифікації моделі. Порядок фіксований
(див. Частину В).

#### Б.2.2. Blacklist категорій + фолдинг у публічні типи (вихід)
- **Де:** `bot_logic.build_simplified_availability` (`bot_logic.py:49-70`); чорний
  список `IGNORE_CATEGORIES = ["Колиба", "Басейн", "Overbooking"]` (`bot_logic.py:18`).
- **Що запускає:** будь-яке перетворення сирого виходу скрапера в доступність для
  клієнта.
- **Що робить:** (а) викидає заблоковані категорії; (б) **згортає** десятки внутрішніх
  OtelMS-підтипів (`"Стандарт сімейний В+Д"`, `"Стандарт 4х 2Л + Д"`…) у лише **3
  публічні типи** (`public_room_type`, `bot_logic.py:36-46`), сумуючи лічильники.
  Так внутрішні назви кімнат **ніколи не витікають** у відповідь, а модель у промпті
  окремо позбавлена права їх вигадувати (`bot_server.py:170`).

#### Б.2.3. Анти-спам дедуплікація вихідних повідомлень
- **Де:** `bot_server.py:791-819` (`_emit` + `recent_bots`).
- **Що запускає:** відповідь, що повторює одне з останніх 2 повідомлень бота (типово
  drip-burst повторно тригерить той самий FAQ).
- **Що робить:** порівнює **кожну** частину `[SPLIT]`-відповіді з нещодавніми; якщо всі
  повторюються — придушує відправку (`"…suppress (anti-spam)."`). Це запобігає
  «зацикленню» бота на однаковому тексті.

#### Б.2.4. Нормалізація/деінфляція кількості гостей (вхід після LLM)
- **Де:** `bot_server.py:481-483`; `bot_logic.normalize_rooms_for_total` (`536-559`) і
  `collapse_duplicate_group_rooms` (`635-675`).
- **Що запускає:** типова помилка малого LLM — розкласти «2 номери для 4 дорослих» як
  4+4=8 осіб, або продублювати всю компанію на кожну дату-вибір («15 чи 16 липня»).
- **Що робить:** детерміновано перечитує з тексту клієнта явну кількість номерів і
  сумарну кількість дорослих та перерозподіляє; згортає дубльовані over-capacity
  кімнати в одну. Запускається **до** підрахунку великої групи, щоб не роздути
  компанію штучно.

### Б.3. Валідація відповідей

#### Б.3.1. Жорсткий парсинг JSON (grounding відповіді LLM)
- **Де:** `dialogue_engine.parse_slots` (`60-86`) — див. А.1.
- **Поведінка при збої:** будь-яка невалідність (порожньо, не-JSON, не-`dict`,
  «stringy-null») → безпечний фолбек `{"topic": "greeting", "rooms": []}`, після
  якого бот просто перепитує бракуючі дані замість того, щоб діяти на «сміттєвих»
  слотах.

#### Б.3.2. Гейтинг доступності — «ніколи не котирувати зайняте»
- **Де:** `dialogue_engine.finalize_quote` (`811-883`); `bot_logic.is_room_available`
  (`124-143`); `_stay_all_free` (`dialogue_engine.py:415-429`).
- **Що запускає:** формування котирування ціни на конкретні дати.
- **Що робить:** ПЕРШ ніж рахувати ціну, перевіряє календар. Статус кімнати —
  `available` / `sold_out` / `unknown`. **Дата, відсутня в скрейпі, вважається зайнятою
  (лічильник 0)** — бот ніколи не котирує дату, яку OtelMS не підтвердив вільною
  (`bot_logic.py:139-143`).
- **Поведінка при спрацюванні (шлях деградації):**
  - зайнято, але вільні інші категорії → крос-сел `ROOM_BOOKED`;
  - зайнято все → найближче вільне вікно `SOLD_OUT_FOUND_NEAREST`, інакше `NEAREST_NONE`;
  - дата **поза** вікном скрейпа → `unknown`, котирування триває (не блокуємо far-future).

```python
status = bot_logic.is_room_available(simplified_availability, room_type, nights)
if status == "sold_out":
    if len(rooms) == 1:
        return _soldout_reply(r, simplified_availability, ubd_booking)
    sold_out.append(r); continue
```

#### Б.3.3. Гейт фізичної місткості кімнати
- **Де:** `pricing_engine.fits_room` (`213-228`), виняток `OverCapacityError`
  (`86-88`); кидається в `quote` (`319-322`), ловиться в `finalize_quote`
  (`dialogue_engine.py:850-854`).
- **Що робить:** якщо тип кімнати фізично не вміщує компанію (Стандарт: ≤3 дорослих-екв.
  і ≤4 особи; Напівлюкс: ≤5), він **виключається** з пропозиції; для мультикімнатного
  бронювання показується `ROOM_TOO_SMALL` із проханням перерозподілити (не «мовчазне»
  відкидання інших валідних кімнат).

#### Б.3.4. Гейт міжсезоння (off-season)
- **Де:** `pricing_engine.OffSeasonError` (`82-83`), `stay_is_priced` (`160-168`),
  `PRICED_MONTHS = {6,7,8}` (`71`); гілка в `dialogue_engine.plan` (`623-631`) і
  `has_off_season_dates` (`399-404`).
- **Що робить:** якщо будь-яка ніч припадає на непріайсений місяць — ціна не
  вигадується; повертається `OFF_SEASON` («вартість ще узгоджується»), а `bot_server`
  тегує розмову `Instagram` для людини (`bot_server.py:787-789`).

#### Б.3.5. Guard «немає підтвердженого перебування» (Bug 2)
- **Де:** `bot_server.py:675-684`; `bot_logic.has_committed_stay` (`586-603`),
  `mentions_nights_range` (`581-583`), `is_vague_availability_probe` (`575-578`).
- **Що робить:** бот **не скрейпить і не заявляє «зайнято»** без явних дат/тривалості.
  Розпливчастий запит («ще є вільні місця?») або діапазон ночей («днів 4-5») → просить
  точні дати (`QUESTION_ONLY_DATES`), а не котирує вгадане перебування.

#### Б.3.6. Guard «дати в минулому» (data-driven, без годинника)
- **Де:** `dialogue_engine._stay_before_calendar` (`382-387`), `_past_dates_reply`
  (`390-391`); виклик у `finalize_quote` (`831-832`) і `finalize_quote_all` (`952-953`).
- **Що робить:** якщо запитаний заїзд раніший за все, що показує календар, це минулі
  дати → `PAST_DATES`. Рішення **керується даними скрейпа**, а не системним часом, тож
  бот ніколи не каже «все зайнято» для стею, який просто вже минув.

### Б.4. Обмеження / структуризація контексту (grounding входу)

#### Б.4.1. Промпт як контракт: «лише JSON, лише екстракція»
- **Де:** `EXTRACTION_PROMPT` (`bot_server.py:158-251`).
- **Що робить:** обмежує LLM жорсткою JSON-схемою з переліком дозволених значень,
  забороняє markdown/прозу/внутрішні назви кімнат, змушує консолідувати слоти з усієї
  історії (анти-амнезія). Це grounding **на вході** — модель не має «свободи» вигадувати
  формат чи вміст.

#### Б.4.2. Детерміновані override-и класифікації LLM
- **Де:** `bot_server.py:540-552`.
- **Що робить:** надто важливі/часто плутані наміри перекриваються кодом **поверх** теми
  від LLM:
  - велика група (`looks_like_large_group` або `slots_total_guests >= LARGE_GROUP_MIN=20`)
    → примусово `topic="group_event"` (`bot_server.py:542-544`);
  - явний FAQ (локація/оплата/їжа/…) → `faq_override` пінить тему `faq` і шаблон
    (`bot_server.py:548-552`, `bot_logic.faq_override` `888-930`).

#### Б.4.3. Слот-пам'ять (анти-амнезія на рівні Python)
- **Де:** `_slot_memory` (`bot_server.py:314`); `bot_logic.merge_rooms` (`1030-1056`),
  `merge_room` (`991-1012`), `remember_rooms` (`1059-1061`); виклики
  `bot_server.py:485-524`.
- **Що робить:** малий LLM іноді «губить» уже названий слот; Python пам'ятає кімнати
  бронювання по розмові й **дозаповнює** порожні поля з пам'яті (нові непорожні значення
  завжди перемагають). Так бот не перепитує вже надане й не забуває 2-гу/3-тю кімнату.

#### Б.4.4. Детермінований фолбек парсингу дат
- **Де:** `bot_logic.parse_date_request` (`429-486`); виклик `bot_server.py:492-501`.
- **Що робить:** коли LLM **впустив** дату, надіслану одразу після пропозиції розбиття
  групи, чистий регекс-парсер (спрацьовує ЛИШЕ на явну назву місяця або дату з крапкою,
  ніколи на «голе» число) відновлює `checkin`, щоб бот не мовчав.

#### Б.4.5. Детермінований розрахунок харчування (без арифметики LLM)
- **Де:** `bot_logic.parse_meal_request` (`360-387`); `pricing_engine.meal_cost`
  (`433-455`); `dialogue_engine.finalize_meals` (`1097-1126`).
- **Що робить:** вартість харчування рахується формулою `unit × persons × days` у
  Python, а не моделлю — ще один винос числової логіки з LLM у тестований код.

### Б.5. Захист від гонок / дублікатів (надійність асинхронного шару)

#### Б.5.1. Serialize + drip-burst dedup (супресія застарілих відповідей)
- **Де:** `bot_server.py:312-352`; `_conv_locks`, `_conv_seq`, `_next_seq` (`331-333`),
  `_superseded` (`336-339`).
- **Що запускає:** кілька повідомлень «пачкою» (клієнт пише по частинах) або
  дабл-фаєр вебхука.
- **Що робить:** кожному вхідному присвоюється `seq`; `asyncio.Lock` серіалізує обробку
  per-conversation; **лише найновіше** повідомлення в пачці формує відповідь
  (`_superseded` перевіряється на вході, всередині й перед відправкою —
  `bot_server.py:349, 781-783`). Пачка згортається в ОДНУ консолідовану відповідь, а
  корекція «на льоту» перемагає застарілий котирувальний результат.

## ЧАСТИНА В. Керуючий алгоритм надійності як потік рішень

Нижче — впорядкований потік обробки одного вхідного повідомлення (основа для
блок-схеми). Точка входу — вебхук `@app.post("/webhook")` (`bot_server.py:894`) →
`process_incoming_message` (`342`) → `_handle_incoming` (`355`). Кожен «аварійний
вихід» означає `return` без подальшої обробки.

### В.0. Прийом вебхука (`bot_server.py:894-925`)
1. Розпарсити JSON? — **ні** → вихід `{"status":"ignored"}`.
2. `event=="message_created"` і `message_type in ("incoming",0)`? — **ні** → лог і `{"status":"ok"}`.
3. Приватна нотатка? — **так** → `{"status":"ok"}`.
4. Є `conversation_id` і (`content` або вкладення)? — **так** → присвоїти `seq`, поставити
   `process_incoming_message` у `BackgroundTasks`; одразу повернути `{"status":"ok"}`.

### В.1. Серіалізація (`process_incoming_message`, `bot_server.py:342-352`)
5. Взяти per-conversation `Lock`.
6. `_superseded(seq)`? (прийшло новіше) — **так** → **аварійний вихід** (відповість новіше).

### В.2. Детерміновані short-circuit guard-и (`_handle_incoming`, порядок фіксований)
Порядок: `mute → cooldown → barter → spam → payment → phone → booking.com`.

7. **Mute-мітка** (`Замовлено`/`Позначено`)? (`:360-363`) — **так** → **STOP** (людина веде).
8. **Кулдаун < 5 хв** після збою LLM? (`:367-370`) — **так** → **STOP** (мовчимо).
9. **Бартер**? (`:375-378`) — **так** → мітка `Instagram`, **STOP** (мовчазний хендоф).
10. **Спам/B2B**? (`:381-383`) — **так** → **STOP** (ігнор).
11. **Оплата** (скрін/ключові слова)? (`:387-394`) — **так** → `PAYMENT_RECEIVED_HANDOFF`
    + мітки `Замовлено`+`Instagram`, **STOP** (ніколи не авто-підтверджуємо).
12. **Телефон**? (`:397-400`) — **так** → `PHONE_RECEIVED`, **STOP**.
13. **Booking.com**? (`:405-409`) — **так** → `BOOKING_COM` + мітка `Instagram`, **STOP**.

### В.3. Історія та «остання відповідь» (`:411-447`)
14. Прочитати історію Chatwoot; зібрати `dialogue_history` і `client_history`.
15. **Чиста подяка/прощання** (`is_pure_thanks`)? (`:434-447`) — **так** → відповісти на
    незакритий FAQ (якщо є) + `ACKNOWLEDGE_THANKS`, **вихід** (бот завжди має останнє слово).

### В.4. Екстракція LLM (з circuit breaker) (`:449-471`)
16. Сформувати промпт (підстановка `%%TODAY%%/%%HISTORY%%/%%MESSAGE%%`).
17. `generate_with_retry` (ретраї 2s/4s на транзієнтних збоях) → `parse_slots`.
18. Виняток (LLM недоступний)? — **так** →
    - `_superseded`? → вихід;
    - інакше: `ERROR_LLM_DOWN` (з дедуплікацією) + мітка `Instagram` + старт кулдауну,
      **аварійний вихід деградації**.
19. Успіх → `slots` (валідний dict; при поганому JSON — безпечний `greeting`).

### В.5. Постобробка слотів у Python (grounding) (`:473-606`)
20. `normalize_rooms_for_total` + `collapse_duplicate_group_rooms` (деінфляція гостей).
21. `merge_rooms` зі слот-пам'яттю (дозаповнення втрачених полів).
22. Детермінований фолбек дати (`parse_date_request`), якщо LLM впустив дату.
23. Guard діапазону ночей (Bug 2): зняти вгадані `nights`/`checkout`.
24. Обчислити `slots_changed` (чи змінилось бронювання цим ходом).
25. Override-и: велика група → `group_event`; явний FAQ → `faq` (перекривають LLM).
26. Контекстні наміри за попереднім повідомленням бота: прийняття розбиття, `bare "Так"`
    (→ `booking_confirm`/прийняте вікно), захист від передчасного IBAN.
27. `topic=="barter"` (спіймав екстрактор)? → мітка `Instagram`, **STOP**.
28. `topic=="unknown"`? → `MANAGER_HANDOFF` + мітка `Instagram`, **STOP** (єдиний
    хендоф за наміром).

### В.6. Детермінований роутинг і відповідь (`:624-752`)
29. `route_simple_topic` (`bot_server.py:263-283`): проста тема → фіксований шаблон
    (group/thinking/reject/booking_confirm/presentation/FAQ); інакше `None` → шлях
    бронювання.
30. Спец-гілки: харчування (детермінований розрахунок), `BED_CONFIG` з датами →
    реальна доступність з сирого скрейпа.
31. Якщо `reply is None` → `dialogue_engine.plan(slots)` → `action ∈ {reply, quote,
    quote_all, explore, nearest}`:
    - Guard Bug 2: `quote/quote_all` без підтвердженого перебування → просити точні дати.
    - Запам'ятати запропоноване розбиття / режим «немає дат» → проактивний скан.
    - Якщо `action` — **скрейп-дія** (`quote/quote_all/explore/nearest`):
      - `slots_changed==False` і не «пошук найближчих»? → **не скрейпимо** повторно
        (chit-chat): або віддати з кешу, або мовчазний вихід (`bot_server.py:704-728`).
      - інакше: (перший хід) привітатись → «Секундочку…» → `get_hotel_data_cached`
        (кеш TTL 900с) → `build_simplified_availability` → `build_booking_reply`.
      - Немає даних доступності? → холдинг «технічна затримка бази», **вихід**.
    - інакше `reply = decision["reply"]` (питання/шаблон).

### В.7. Гейти й фінальна відправка (`:754-892`)
32. Анти-дедлок пусті слоти (`QUESTION_ALL_MISSING` → півот на питання про гостей).
33. Наполягання на віці дітей (лише реальна дитина невідомого віку).
34. `_superseded`? (прийшло новіше під час обробки) — **так** → **аварійний вихід**
    (супресія застарілої/подвійної відповіді).
35. Off-season у відповіді? → мітка `Instagram` для менеджера.
36. `_emit` для кожного повідомлення: **part-aware анти-спам дедуп** (придушити
    повтори), нота про тваринку (+300 грн), префікс-привітання на першому ході,
    розбиття `[SPLIT]` і відправка через `_deliver` з паузою 1.5 с.
37. Порядок відправки: **Greeting → інші FAQ пачки → (харчування) → основна відповідь
    → добронювальний extra** (`bot_server.py:826-890`).
